bench_jgrapht_hashgraph -- JGraphT 1.5.3 BreadthFirstIterator on DirectedPseudograph, column "jgrapht_hashgraph"

USAGE
  bench_jgrapht_hashgraph --source <s> --target <t> [--query <id>] [--tag <text>] [--repeats <k>] <instance.gr>
  bench_jgrapht_hashgraph --header       (JAVA_HOME optional)

WHAT IS TIMED
  Draining a BreadthFirstIterator from s (the whole reachable region), on a
  DirectedPseudograph (an object per arc, hash maps around it) that was filled
  arc by arc OUTSIDE the clock (build_ms), as the first campaign of 2026-10-11
  did for every library; ../jgrapht is the second campaign's driver, on jgrapht-opt's CSR graph
  built inside the clock.  Before the clock the same iterator is run on a
  synthetic graph (a seeded random digraph, m = 4n) until the JIT is quiet.
  Clock: the solver THREAD's CPU time (ThreadMXBean), NOT including the
  garbage collector's pause time; proc_ms is the whole process (10 ms ticks).
  JVM flags: -Xmx45g -XX:ActiveProcessorCount=1 -XX:+UseSerialGC.

COLUMNS (one CSV row per run; --header prints the header line alone)

  instance      base name of the .gr file
  nodes, arcs   from its problem line
  query         the id passed with --query (0 if none)
  source,target the pair passed on the command line, DIMACS ids 1..n; the
                search starts at source and settles everything reachable, the
                target is only looked up afterwards
  repeat        1 (every campaign repeat ran in its own process; --repeats k
                prints k rows)
  status        REACHED      the search finished and the target was reached
                UNREACHABLE  the search finished and the target was not reached
                BAD_PATH     the parent chain from the target does not lead back
                             to the source, or disagrees with the reported depth
                MEMORY       (Python programs) the address-space cap was hit
  reached       1 if the target was reached, else 0
  hops          depth of the target (number of arcs on the BFS path); -1 where
                the program cannot read it off (the functional exports)
  dist          the same number (the graphs are unweighted for this study)
  cpu_ms        THE MEASUREMENT: CPU time between the two clock readings
  cpu_usr_ms, cpu_sys_ms   its user/system split
  proc_ms       whole-process CPU time over the same window (equal to cpu_ms
                for native programs; for JVM programs it also counts the JIT
                compiler threads and is a diagnostic, not the measurement)
  wall_ms       wall-clock time over the same window; nothing is derived from it
  parse_ms      CPU time spent reading the file, OUTSIDE the clock
  dedup_ms      0.000 on every row of this study (nothing is collapsed: parallel
                arcs change no BFS answer)
  build_ms      CPU time spent marshalling the parsed arrays into the input the
                solver takes, OUTSIDE the clock (0.000 where the solver takes
                the arrays themselves)
  tag           free text copied from --tag (the campaign put "<family>;rep=<k>" there)
  (no clock_build_ms/clock_solve_ms columns: nothing is built inside the clock)

EXAMPLE (the first campaign's raw row for the same instance)
  Square-n.10.0.gr,1024,3968,0,14,787,1,REACHED,1,8,8,0.699,0.000,0.699,0.000,0.688,4.475,0.000,14.363,Square-n;rep=1

The published raw rows (published_results/bfs_results.zip, <column>/raw/<family>.csv)
carry two further columns appended by the campaign runner, inferred_from and
core, which the program itself does not print.
