bench_sml_csr -- the verified CSR DFS export in Standard ML (MLton), column "sml_csr" (paper: SML CSR)

USAGE
  bench_sml_csr --source <s> --target 0 [--query <id>] [--tag <text>] [--repeats <k>] <instance.gr>
  bench_sml_csr --header

WHAT IS TIMED
  One call of dfs_edges_run on the two arc arrays read from the file (vertex
  count nodes+2, see the comment in main_csr.sml): the CSR build, the cursor
  array, the stack, the seen array and the search are all inside the call.
  Reading the file is outside.  Clock: process CPU time (getrusage, user+sys).
  The export returns its stack, not its seen array, so visited is -1; an
  empty stack is a sweep that ran to exhaustion (status OK).

COLUMNS (one CSV row per run; --header prints the header line alone)

  instance      base name of the .gr file
  nodes, arcs   from its problem line
  query         the id passed with --query (0 if none)
  source        the source passed on the command line, a DIMACS id 1..n
  target        the target passed on the command line.  It must NOT be a
                vertex of the graph; the campaign passed 0, so that the
                reachability exports run until their stack is empty and
                settle everything reachable from the source.  Every program
                refuses a target inside [1, n].
  repeat        1 (the campaign ran every repeat in its own process, so this is
                always 1 in the published raw data; --repeats k prints k rows)
  status        OK           the search ran to exhaustion and the verdict was
                             checked: the (absent) target was not reached
                RAN          the search ran to exhaustion; the SML lists and
                             RBT exports expose no verdict, so nothing more
                             is claimed
                BAD_TARGET   the solver reported reaching the target, which
                             cannot happen
                MEMORY       (Python programs) the address-space cap was hit
  reached       0 if the target was not reached, 1 if it was, -1 if the
                export cannot say
  visited       number of vertices settled (the cross-check between solvers;
                a property of graph and source alone), -1 if the export
                cannot report it
  cpu_ms        THE MEASUREMENT: CPU time between the two clock readings
  cpu_usr_ms, cpu_sys_ms   its user/system split
  proc_ms       whole-process CPU time over the same window (equal to cpu_ms
                for native programs; for JVM programs it also counts the JIT
                compiler threads and is a diagnostic, not the measurement)
  wall_ms       wall-clock time over the same window; nothing is derived from it
  parse_ms      CPU time spent reading the file, OUTSIDE the clock
  dedup_ms      0.000 on every row of this study: nothing is collapsed, a
                parallel arc changes no reachable set
  build_ms      CPU time spent marshalling the parsed arrays into the input
                the solver takes, OUTSIDE the clock (0.000 where the solver
                takes the arrays themselves)
  tag           free text copied from --tag (the campaign put "<family>;rep=<k>" there)

EXAMPLE (Square-n.10.0.gr, the campaign's source 359)
  instance,nodes,arcs,query,source,target,repeat,status,reached,visited,cpu_ms,cpu_usr_ms,cpu_sys_ms,proc_ms,wall_ms,parse_ms,dedup_ms,build_ms,tag
  Square-n.10.0.gr,1024,3968,0,359,0,1,OK,0,-1,0.147,0.000,0.147,0.147,0.121,0.902,0.000,0.000,Square-n;rep=1

The published raw rows (published_results/dfs_results.zip, <column>/raw/<family>.csv)
carry two further columns appended by the campaign runner, inferred_from and
core, which the program itself does not print.
