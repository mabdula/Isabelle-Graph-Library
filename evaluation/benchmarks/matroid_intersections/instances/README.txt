INSTANCES OF THE MATROID INTERSECTION STUDY -- where every file came from
=========================================================================

Three families, generated by the first DIMACS Implementation Challenge's
assignment generators exactly as the Network Flows 2.0 challenge prescribes,
on a ladder of powers of two from 32 upward, five seeds (1-5) per size:

HOW TO OBTAIN
  Generators  ../setup_instances.sh fetches assign.c, dcube.c, twocost.a and geomasn.a (and the
              depository's readme) from the First DIMACS Challenge depository at
              archive.dimacs.rutgers.edu (URLs and md5 in the script) and makes the
              patched copies that compile today; `make' in generators/ builds them.
  Instances   not distributed: regenerate them with generators/gen_instances.sh and
              gen_geometric.sh (then stamp_instances.sh for the .bmatch files) for the
              sizes and seeds listed in seeds/<family>.txt and compare with
              MD5SUM_instances.txt.

1. low-cost   assign.c: nodes N, sources N/2, degree round(2 log2 N),
              maxcost 100, seed K.  n = 32 .. 32768.  m = n log2 n arcs.
2. two-cost   the same assign output piped through twocost.a (costs > 50
              become 10^8, costs <= 5 become 10^2), with the problem line
              split off the banner twocost.a glues it to.  n = 32 .. 32768.
              SAME GRAPHS as low-cost, other costs.
3. geometric  dcube.c: nodes N, dimension 2, maxloc 1000000, seed K, piped
              through geomasn.a (complete bipartite graph, N/2 a side, cost
              = truncated Euclidean distance) with its "e" arc letter
              rewritten to "a".  n = 32 .. 4096.  m = n^2/4 arcs.

  generators/ holds, once ../setup_instances.sh has fetched them, the pristine downloads (assign.c, dcube.c, twocost.a,
  geomasn.a; provenance and md5 in the paper's code references 3, 4, 5:
  https://archive.dimacs.rutgers.edu/pub/netflow/generators/network/assign.c
  .../network/twocost.a, .../matching/dcube.c, .../network/geomasn.a), the
  patched sources that compile today (assign_patched.c, dcube_patched.c, made
  by setup_instances.sh from assign.c.patch and dcube.c.patch; the patch is the only change: includes, declarations, exit(1), %ld, MAXNODES),
  a Makefile, and the scripts gen_instances.sh and gen_geometric.sh as run
  (paths made relative, marked).  seeds/<family>.txt gives, for every
  instance of the grid, the exact generator input and the capacity seed.

CAPACITIES (b-matching).  There is no DIMACS b-matching format; the .bmatch
  file of an instance is its .asn file with capacities stamped on by
  generators/stamp_capacities.py (run through stamp_instances.sh):
      cap(v) = min(U, deg(v)),  U uniform in 1..20, drawn per vertex in
      ascending vertex id with Python's random.Random(K), K the instance's
      own seed index (the _s<K> of the file name); --max 20.
  The graph, the arc order and the comments are untouched; the problem line
  becomes "p bmatch n m" and a comment records the rule and the seed.  The
  matching and weighted matching problems read the .asn file (all
  capacities 1), the b-matching problems the .bmatch file.

FORMAT  DIMACS assignment format (the Flow Challenge 2.0's
  description, https://coral.ise.lehigh.edu/flow-challenge-2-0/wbm-definition-and-format/), with "n <id> <cap>"
  lines and "p bmatch" accepted: c comments, p asn <nodes> <arcs>,
  n <id> [<cap>], a <u> <v> [<w>] with u on the left and v on the right.

CHECKING  MD5SUM_instances.txt: md5, size and path of all 300 files of the
  timed grid (150 .asn and 150 .bmatch).  generators/Makefile says how to
  regenerate them; the two smallest sizes of every family were regenerated
  on 2026-10-29 with this package and matched byte for byte.  The study's
  instance tree also held seeds 6-10 and n = 50000 (inherited from the
  Hungarian study) and a validation set val_n<N>_s<K>; none of those are
  in the tables.
